# Layer 1, slice 0: repository skeleton

## Problem

Every later Layer 1 slice needs the same base: a workspace with the `web/` and `contracts/` sub-projects, one verification command, a database migration path, and CI that runs it all on each pull request. Slice 0 builds only that base, so slice 1 (organisations, projects and people) starts on a tested foundation. It delivers no story. It is the base the design's build order names (design-architecture#build-order).

## User stories

None. Slice 0 is the base for the stories in slices 1 to 14 (design-architecture#build-order). The people who use it are the agents and developers building those slices.

## Acceptance criteria

| # | Criterion | Verified by |
|---|---|---|
| AC-1 | A fresh clone installs with `pnpm install --frozen-lockfile` on the Node version the repository pins, and installing with a different Node major version fails with a message naming the pinned version. | command: `pnpm install --frozen-lockfile` in CI, and once locally with another Node major version |
| AC-2 | `pnpm verify` at the repository root runs lint, type check, unit tests, the production build and the end-to-end tests for every sub-project, and exits non-zero if any of them fails. | command: `pnpm verify` in CI; a deliberately failing unit test makes it exit non-zero (checked once, not committed) |
| AC-3 | `contracts/` exports the API version (`v1`) and a schema for the health response. The schema accepts `{ "status": "ok", "apiVersion": "v1", "database": "ok" }` and rejects a body with a missing field, an unknown `status`, or another `apiVersion`. | test: `contracts health schema` |
| AC-4 | `GET /api/v1/health` returns 200 and a body that the `contracts/` health schema accepts, with `database: "ok"`, when the database is reachable and migrated. | test: `health reports ok with a migrated database` |
| AC-5 | When the database cannot be reached, `GET /api/v1/health` returns 503 with `status: "unavailable"` and `database: "unavailable"`, and the body holds no connection string, host name, stack trace or driver error text. | test: `health reports unavailable without leaking details` |
| AC-6 | The home page has `lang="en-GB"`, a page title, one `h1`, a `main` landmark, and no axe violations at the WCAG 2.2 AA rule set. At 320 CSS pixels wide it has no horizontal scroll. | test: `home page passes axe` and `home page fits 320px` |
| AC-7 | The schema change is a migration file generated by `drizzle-kit generate` and committed. CI applies it to a fresh Postgres with `drizzle-kit migrate` over the direct (unpooled) URL, in a step separate from the build. Applying it a second time changes nothing. | command: the CI migrate step, run twice |
| AC-8 | A GitHub Actions workflow runs on every pull request and on pushes to `main`: install, migrate, then `pnpm verify`, against a Postgres service container. It fails the pull request when any step fails. The existing `process` workflow is unchanged. | command: the workflow run on this slice's pull request |
| AC-9 | No secret is committed. `.env.example` lists `DATABASE_URL` (pooled) and `DATABASE_URL_UNPOOLED` (direct) with placeholder values, and `.env` and `.env.*` other than `.env.example` are ignored by git. | test: `env files are ignored and the example holds no secrets` |
| AC-10 | `AGENTS.md` names `pnpm verify` as the verification command (WA-001) and the Node version the repository pins. | command: read `AGENTS.md` in review |

A test cites a criterion as `layer1-skeleton#AC-3` in its title or a comment. Only `test:` criteria need a citing test.

## Scope

- In:
  - A root pnpm workspace (`package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`), with the Node version pinned in `.nvmrc` and `engines`.
  - `contracts/`: TypeScript package exporting the API version and the health response schema (zod).
  - `web/`: a Next.js app (App Router) with the home page, `GET /api/v1/health`, a Drizzle schema with one table that the health check reads, its generated migration, and Drizzle configuration that reads the two database URLs.
  - Lint, type check, Vitest unit tests, Playwright end-to-end tests with axe, and the root `verify` script.
  - `.github/workflows/verify.yml`, `.env.example`, `.gitignore` entries, and the `AGENTS.md` verification line.
- Out:
  - `runner/`, `extensions/` and `unreal/` (slices 6, 7, 11, 12 and Layer 2).
  - Sign-in, roles, any project data, the command layer and the activity log (slices 1 and 2).
  - Choosing the hosted Postgres provider and region, creating a Vercel project, and any preview or production deployment. These wait for the provider decision below and are outward actions that need the approver.
  - Visual design beyond a plain accessible page.

## APIs and assumptions

- Versions, read from the npm registry on 2026-11-12, all pinned exactly in the lockfile: Next.js 16.4.6, React 19.3.1, TypeScript 7.0.2, drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23.1, zod 4.6.7, Vitest 5.1.0, @playwright/test 1.65.0 with the pre-installed Chromium, @axe-core/playwright 4.14.0, ESLint 10.14.0, pnpm 12.18.0. Node 26.13.1, the current LTS release from nodejs.org.
- Each API the code uses is checked against the installed package's type definitions or bundled docs before use (WA-006, NEXT-001), and the spec records any that differ from expectation.
- Drizzle is chosen over Prisma because Prisma 8 is still a release candidate (decision-system-shape notes; PG-005 pins the ORM major version).
- Assumptions that could be wrong:
  - [assumed] Vercel's Node.js runtime supports Node 26. Settle by reading Vercel's supported Node versions before the first deployment; if it does not, pin the newest LTS it supports and amend AC-1.
  - [assumed] Next.js 16.4.6 builds and type-checks with TypeScript 7.0.2, and its ESLint configuration works with ESLint 10. Settle on the first install; if not, pin the newest versions that work together and record why.
  - [assumed] The pre-installed Chromium works with @playwright/test 1.65.0. If not, launch with the installed browser path as the environment notes describe.

## Non-functional requirements

- Accessibility: WCAG 2.2 AA from the first page (WEB-001, WEB-002), checked by axe in CI.
- Security: no secrets in the repository (SEC-001); the health endpoint never returns connection details (AC-5); database URLs are read from the environment and validated at start-up (SEC-002).
- Migrations: generated, reviewed and applied by the pipeline only (PG-001, PG-003). No `drizzle-kit push` against any database other than a disposable local one.
- Supported browsers for end-to-end tests: Chromium in CI. Other browsers are added when a slice needs them.

## Delivery

- Plan item: design-architecture#build-order, slice 0.
- Pull requests: added as each is opened. Planned as two: the failing tests with stubs (recorded in `tests-commit`), then the implementation that makes them pass.

## Risks and decisions

- **Hosted database provider and region (approver's decision, needed before slice 1 holds real data).** The decision notes want the record in the region nearest the studio and the protected store in Canada if offered (decision-project-record-model, decision-protected-store). Slice 0 uses only a Postgres service container in CI, so it does not depend on this choice. The candidates and their regions are to be checked and put to the approver before slice 1 deploys.
- **Node and TypeScript majors.** Taking the newest majors follows the approver's preference for the latest versions. The assumptions above say how each is checked, and what happens if one does not work.
- **The CI workflow becomes a required check.** Making `verify` required in branch protection is the approver's setting to change. This spec only recommends it.
